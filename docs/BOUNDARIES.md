# pi-dstack-notify and future pi-dstack-loop-tools boundaries

The notify export preserves one existing TypeScript core/policy. The minimal entry delegates to the shared factory. The minimal static relative-source/type closure is recorded with final hashes in the external candidate packet. The settled second product is future `pi-dstack-loop-tools`, grouping reminders and bounded SAME-session continuation as independently enabled capabilities—not a third package or general scheduler.

## Shared modules are not enabled features

Required imports include internal Owner request/control/evidence/observation code, reminder time/planning/workflow support, reminder scheduler and advisory poke code/types. The shared factory and existing policy use these leaves; deleting them to shrink packaging would be a refactor, not a privacy transformation. They may be retained as internal dependencies with the following hard default-root limits:

- Only `notification_publish` and `notification_publish_fyip` are registered.
- No OWNER/reminder/poke tools or controllers are created through the minimal branch.
- No automatic reminder timer, poke timer, scheduler service or model request is started.
- No alternate inner FULL activation manifest is distributed.
- Internal full-factory regression tests do not advertise a supported second activation route.

Historical frozen reader source, if retained, is a test-only compatibility fixture—not a second runtime policy engine or a migration/activation shortcut. Preserve version-fence rejection and uncertainty cases.

Registration separation is cheap; actual core/storage/API separation is not done. The current service still composes reminder/OWNER methods and planner, and notification FYIP shares exact v3 DDL/marker/fence validation with pending originals/occurrences. Do not drop dormant tables or invent a second ledger/policy to relabel the package. Future loop-tools reminders need explicit original-enrollment/canonical/control/transaction and delivery-provider ownership; a generic publish-text callback cannot preserve those atomicities. Continuation must not use reminder READY/private configuration/Inbox/Telegram as a mandatory readiness gate. Optional coinstalled coordination needs a real trusted contract; no cross-extension provider API or mandatory load order is established by this source. The full loop implementation remains preserved in the original source; no loop split is implemented here.

## Trust and side effects

Tool arguments are assertions, not permission, canonical identity, verified revision or destination override. Native SEND/READ evidence and persistent policy checks remain mandatory. An answer or delivery receipt is not owner approval or a wake request. Unknown side effects are not blindly retried.

Absent configuration must be measured inert on final export bytes. A configured operation is not the same thing as registration or a no-send SDK smoke. Transport operation deadlines are not automatic reminder scheduling.

## Validation contract

Fresh evidence must cover the final allowlist, runtime/import/test/compiler input closure and all output hashes. Preserve meaningful canonical/both-ID/fake-brand/lifetime/cancellation/negative cases. Use real host TypeBox and the actual entry/core with closed native/HTTP fakes; any adapter-only substitutions must be exact-parent isolated and explicitly distinguished.

Strict whole-source no-emit checking must include every selected runtime/test file and retained frozen fixtures, with portable published configs and machine-specific resolution outside the tree. No acquisition is authorized to fill missing tooling.

An actual isolated public SDK **ROOT package** smoke must use final exported bytes/new local SHA, not a direct entry bypass or an earlier original-source run: disposable HOME/cwd/agent directory/auth location, externally scrubbed nonempty offline environment, untrusted in-memory settings/session, no ambient resources, pre-init denial counters, explicit offline ModelRuntime, noTools all, no prompt/tool invocation, exactly two registrations, absent configuration flag, empty resource/custom-provider queues, one start/shutdown and runtime disposal. In-process guards are not an OS sandbox.

Final-candidate producer evidence is retained outside the package. Independent clearance is a separate gate and is not claimed by these documents. Applicable Unicode data attribution and the complete permission notice are included in THIRD-PARTY-NOTICES.md.
